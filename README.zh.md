# 单张消费级 GPU 上的投机解码(Speculative Decoding):到底划不划算?

在单张 RTX 5090 上,对 vLLM 的 `draft_model` 投机解码做的一次测量研究——覆盖并发数(concurrency)1~32,不光跟一个"配套 baseline"比,还跟**真正的默认配置**比。

> 本文件是英文版 `README.md` 的中文对照版,给你自己学习/口头复述用,专业术语保留英文,方便跟教授对话时直接切换。两版内容应该保持一致,以后改动请两边都改。

**核心发现**:在我们测过的每一个并发点上,投机解码都**没能稳定超过真正的默认配置**。它对着一个"配套 baseline"(执行路径被人为拖慢过的对照组)确实有真实、可复现的吞吐提升——但那个 baseline 自己就比默认配置多付了一份"execution-path 降级税"(runtime tax),这份税基本上抵消掉、甚至超过了投机解码带来的收益。

---

## 1. Problem(问题)

投机解码(speculative decoding, SD)理论上能加速自回归(autoregressive)解码——用 GPU 本来闲置的算力,一次验证好几个候选 token,而不是一个一个来。大部分公开评测都在数据中心级 GPU(A100/H100)上做。我们想问一个更窄、更贴近实际部署的问题:

> 在一张消费级 GPU(RTX 5090)上,固定一对模型,打开 vLLM 的 `draft_model` 投机解码,随着并发数上升,吞吐量真的比**用户直接跑默认 vLLM**要高吗?

最后这半句很关键。如果拿一个"稻草人 baseline"去比,很容易得出"有用"的结论。我们坚持要跟**真正的默认 vLLM**比,下面会说明这个坚持为什么改变了答案。

## 2. Setup(实验配置)

| | Target 模型 | Draft 模型 | GPU |
|---|---|---|---|
| 模型组合 | Qwen3-14B-AWQ | Qwen3-0.6B | 1x RTX 5090 |

投机解码配置:`method=draft_model`,`num_speculative_tokens=5`(K=5)。`max_num_seqs=16`,`max_model_len=8192`,`gpu_memory_utilization=0.85`,关闭 prefix caching,greedy decoding,固定短 prompt(输出约 77 个 token)。

我们定义了三种服务器配置(启动脚本在 `scripts/start_*.sh`):

- **A —— 真正的默认 vLLM。**不开投机解码,不做任何手动改动。用户拿到手就是这个样子。
- **S —— SpecDec。**默认 vLLM + `draft_model` 投机解码,K=5。
- **B —— matched baseline(配套 baseline)。**注意,**这不是一个真实会被部署的配置**,它纯粹是为了测量而造出来的对照组。

**为什么需要 B**:打开 `draft_model` 投机解码,会强制 vLLM 退回到一条更老的执行路径——V1 model runner,并且关掉 async scheduling(`VLLM_USE_V2_MODEL_RUNNER=0`、`--no-async-scheduling`)。这是这版 vLLM 实现上的副作用,跟"投机解码这个算法本身"没关系。如果直接拿 S 跟 A 比,我们会把两件事混在一起算:"投机解码有没有用" 和 "被迫走老路径有没有代价"。B 就是用来把第二件事单独隔离出来的——手动复现同样的降级,但**不打开投机解码**。这样,**S vs B** 单独衡量投机解码自己的贡献,**B vs A** 单独衡量"被迫走老路径"这件事本身的代价。

## 3. Measurement protocol(测量方法)

每个并发数 `c`,`run_sweep.py` 负责编排整个流程:本地 prewarm(不在被测量的窗口内)→ 启动远程 telemetry 采样(`scripts/telemetry.py`,约 0.2 秒一次,抓取 Prometheus `/metrics`)→ 跑正式 benchmark(`benchmark.py`,用 `ThreadPoolExecutor` 持续补位式地维持 `c` 个并发,不是"齐步走"式的波次)→ 停止 telemetry。每个"配置+并发数"组合,至少测 64 次请求(`c` ≤ 16 时)或更多。

**时间指标定义**(`benchmark.py` 里逐请求算出来的):
- **TTFT**:从 HTTP 请求发出前一刻,到收到第一个流式 token 的墙钟时间。客户端在韩国,服务器在中国大陆,中间经过 SSH 隧道——所以 TTFT 里包含了跨境往返和建立隧道的时间,不只是服务器自己"生成第一个 token"花的时间。TTFT/E2E 的绝对数值不能当成服务器内部处理延迟来解读,本报告里所有结论都是在同一条网络链路下做的相对比较。
- **E2E**:从请求发出到最后一个 token 的墙钟时间。
- **TPOT**:`(E2E − TTFT) / (completion_tokens − 1)`。这是对"平均每步 decode 花多少时间"的**近似**,**不是真正的逐 token 延迟(true ITL)**——它是整个 decode 阶段的一个平均值,不是每个 token 单独测出来的。当 `completion_tokens ≤ 1` 时会返回 `None`(不是 0),因为第一个 token 是 prefill 的工作,不算 decode。

**投机解码相关指标**(Prometheus 计数器,测量窗口前后做 `after − before` 差值):
- `acceptance_pct = 100 × accepted_tokens / draft_tokens`
- `mean_acceptance_length = 1 + accepted_tokens / drafts`(这个"+1"是 vLLM 每次验证不管中不中都会白送的 bonus token)
- `K_observed = draft_tokens / drafts`(用来验证配置的 K=5 有没有被真实执行)

**排队指标**:`Wait% = 100 × (waiting>0 的采样次数) / (总采样次数)`,其中"活跃采样"定义为 `running > 0 或 waiting > 0` 的那些采样点。这是一个**时间维度**的统计——"在采样到的所有瞬间里,有百分之多少的瞬间,至少有一个请求在排队"——**不是**"有百分之多少的请求经历过排队"。这两者很容易混淆,意思完全不同。

**独立重跑(reruns)**:B 和 S 各自在 c=4 和 c=16 又独立重新启动服务器、重新测了两轮(`rerun1`、`rerun2`),加上原本 c=1,2,4,8,16,32 的完整扫描。A 最初只在 c=1,4,16 测过一次;后来我们审计分析代码时发现了一个方法论上的漏洞(下面会讲),又给 A 在 c=4 和 c=16 各补了两轮独立重跑,凑齐跟 B/S 一样的重复次数。

**日期**:B/S 原始扫描:08-17。A 原始轮 + B/S 两轮重跑:08-22。A 两轮重跑:08-24。**没有任何两个配置是在同一天同一个时间窗口测的**——详见第6节 Limitations 第1条。

## 4. Main result(核心结论)

**我们测过的所有并发点里,没有一个点投机解码能稳定超过真正的默认配置。**

我们把这件事拆成三层看。

### 层① —— S vs B(执行路径一样,只看投机解码自己的贡献)

因为 S 和 B 走的是同一条(被迫降级的)执行路径,这一层单独衡量投机解码本身有没有用。

| c | 1 | 2 | 4 | 8 | 16 | 32 |
|---|---|---|---|---|---|---|
| S vs B | -0.3% | +7.6% | **+13.2%** | +6.6%¹ | **-3.7%** | -0.8% |

c=2~8 都是正收益,c=4 达到峰值。到 c=16 反转为负。三次独立重跑复现:
- c=4:+13.2% / +5.5% / +13.5%(3/3 为正)
- c=16:-3.7% / -7.1% / -18.2%(3/3 为负)

¹ c=8 只测过一次,没有重跑。

### 层② —— B vs A(单纯"被迫走老路径"这件事本身的代价)

| c | 4(三次重跑) | 16(三次重跑) |
|---|---|---|
| B vs A | -16.3% / -4.5% / -23.7% | -23.9% / -11.1% / -13.6% |

B 比 A 慢 4%~24% 不等,六次配对测量**全部**如此。这纯粹是"退回老执行路径"的代价,跟投机解码开没开没关系。

### 层③ —— S vs A(真正对部署者有意义的数字)

计算方式:把 S 的每一次独立测量,跟**编号对应的那一次** A 的独立测量配对(不是拿三次 S 都去除同一个固定的 A 值——下面有更正说明)。

| c | 结果 |
|---|---|
| 1 | -19.7%(A 在这个点只测过一次,没法配对) |
| 4 | -5.2% / **+0.75%** / -13.4% —— 最好情况也只是接近打平,不是真赢;三次里两次清楚为负 |
| 16 | -26.8% / -17.4% / -29.3% —— 3/3 为负,没有例外 |

**更正说明(2026-08-24)**:早期版本的分析曾报告"c=4 打平,在噪声范围内",算法是拿 S 的三次重跑都除以 A 的单次原始测量值。后来我们又给 A 在 c=4/16 补测了两轮独立重跑,发现 **A 自己的 run-to-run 波动(11%~14%)跟 B 是同一量级**——A 一开始被想当然地认为"很稳",其实没有。用配对好的、对应轮次的 A 重新计算后,"打平"这个说法站不住了。上面这版是更保守、也更站得住的更正结论。

## 5. Mechanism(机制)

两条证据能解释"为什么方向会随并发数反转",并且排除了最容易想到的那个错误解释。

**不是"猜测质量变差了"。**`acceptance_pct`(33.3%)和 `mean_acceptance_length`(2.67)在所有并发数、所有独立重跑下**完全恒定**,没有一次例外。如果并发升高会让 draft 模型猜得更差,这两个数字应该随 `c` 上升而下降——但它们没有。也就是说,"猜-验证"这套机制本身,不管负载多高,表现都是一样的。

**是"抢算力"的问题,而且 GPU 利用率直接能看出来。**c=4 时,各配置平均 GPU 利用率只有 47%~70%——算力是有富余的。c=16 时,涨到 78%~90%,接近打满。大模型在低并发时,通常是"显存带宽卡脖子"(memory-bandwidth-bound),不是"算力卡脖子"——GPU 大部分时间在等着把权重搬进来,计算单元反而是闲着的。投机解码的整个价值主张,就是拿这部分闲着的算力,顺手验证好几个候选 token,代价接近于零。一旦并发高到把算力占满,这部分闲置算力就消失了,draft 模型多算的那部分反而要跟真实的批处理任务抢**同一份有限的算力**——投机解码就从"白嫖"变成"倒贴"。

这跟投机解码相关文献里普遍认为的"收益集中在低 batch 场景"是吻合的,而且我们在这块消费级 GPU 上,把这个交叉点具体测了出来——大部分投机解码评测都在显存带宽更高的数据中心 GPU 上做,很少有人报告这个。

**排队细节**:`Wait%` 在 c ≤ 16 的所有采样点、B 和 S、所有重跑里,**恒为 0**——c=16 的反转是纯算力竞争,不涉及排队。到 c=32,`Wait%` 突然升高,`vllm_waiting_capacity` 平均 8~9(`vllm_waiting_deferred` 全程为 0)——这个排队完全是因为撞上了 `max_num_seqs=16` 这个批次上限,跟 c=16 的反转是**不同的机制**,不是同一件事的延续。

## 6. Scope and Limitations(适用范围与局限)

1. **跨日期漂移,而且没有任何两个配置是同一次测的。**B/S 原始扫描:08-17。A 原始轮、B/S 两轮重跑:08-22。A 两轮重跑:08-24。即便是层③里用来配对的"编号"(A-rerun1 配 S-rerun1 这种),对齐的也是"第几次独立测量",**不是"同一天测的"**——"rerun1"这个标签在不同配置之间并不代表同一天。三次独立数值全部分开列出,不合并成平均数或中位数。

2. **run-to-run 波动是真实存在的,而且 A、B、S 三者量级相近**——这本身就是一个发现,不是可以直接平均掉的噪声。B@c16:964.0 / 1125.5 / 1217.9 tokens/sec(波动~26%)。A@c16:1267.1 / 1265.3 / 1409.4(波动~11%)。A@c4:361.0 / 371.3 / 412.0(波动~14%)。A 的稳定性最初是被想当然地假设的,没有实测过;补测之后发现它并不比 B 更稳。所有比较都只在配对好的窗口内做,不会拿不同轮次的绝对值直接混着比。(另外观察到"c=16 三次重跑里,B 的绝对值越高,Δ% 越负"这个单调关系,但只有 3 个数据点,**只记为观察,不当成规律来断言**。)

3. **这个波动的成因未知。**我们没有归因到底是 GPU 降频/温度、宿主机噪声、还是别的原因(比如 AutoDL 这类租用云主机可能存在的"邻居抢资源"效应)。这个问题被放进了 Future Work,而不是简单地多测几轮把它平均掉(见第7节)。

4. **单一 workload。**固定短 prompt,输出约 77 个 token,TTFT 占 E2E 约 39%——decode 在总请求时间里占比相对较小。基于 decode 阶段优化带来的加速,可能被一份比例较大、固定不变的 prefill 成本系统性稀释了。第7节里的"输出长度扫描"就是为了直接验证这一点。

5. **跨境网络链路。**客户端在韩国,vLLM 服务器在中国大陆,经过 SSH 隧道连接;TTFT 计时是在连接建立**之前**就开始的。所以 TTFT/E2E 的绝对值里包含跨境往返和隧道开销,不能当成服务器内部延迟来解读。本报告里所有比较都是在同一条(固定不变的)网络链路下做的相对比较,A/B/S 之间这条链路是完全一致的。

**另外需要说明**:投机解码带来的 KV cache 容量下降(观测到容量大约减半,~101,520 → ~54,192 个 token 槽位,原因是要为 draft/verify 缓冲区预留空间)是一个**独立的、长上下文部署场景下的代价**。我们这次 workload 里,KV 利用率峰值即便在 c=32 也从没超过约 3%(B)/ 2.6%(S)——离这个容量上限还差得很远,所以它没有影响本报告里的任何结论。它对另一种(长上下文)部署场景是真实的代价,这里特意单独说明,避免跟第4、5节的结论混在一起。

## 7. Future work(后续方向)

- **K sweep**(K=1/3/7 × c=1/4/16)。K 直接控制"降级税"和"投机解码自身贡献"之间的平衡。待验证的问题:最优 K 会不会随并发数迁移?更小的 K 能不能让 S 在 c=4 真正超过 A,而不只是打平?
- **输出长度扫描。**当前 decode 在总延迟里占比不高(见第6节第4条)。待验证的假设:更长的输出,能不能把固定的降级税摊薄到更多 decode 步骤上,从而让 S vs A 在低并发下翻正——即便现在没有翻正?如果成立,结论会从"在这块硬件上不划算"精确化为"短输出场景下不划算"。
- **run-to-run 波动归因。**A/B/S 都有 10%~26% 的 run-to-run 吞吐波动,成因未知。比起继续多测几轮把它平均掉,更有价值的下一步是在测量期间记录 GPU 时钟频率/温度曲线,看是否跟波动相关。
- **kernel 级机制验证。**第5节里的 GPU 利用率解释,是靠"排除法"(排除猜测质量下降)加上一个聚合利用率指标推出来的,不是通过 vLLM scheduler 和 model runner 的 kernel 级 profiling trace 验证的。做一条 profiler 驱动的因果链(调度决策 → 执行行为 → GPU 指标 → crossover)可以直接确认它。
- 其他 draft 模型规模对比、任务多样性(对话/摘要/代码)、adaptive K 策略。

## 8. 代码审计中发现的问题

- **KV-cache 列名 bug**,在 `archive/summarize_specdec_formal.py` 和 `archive/compare_b_vs_specdec_formal.py`(已被取代,留在 `archive/` 里存档)里:两个脚本都读取一个叫 `vllm_kv_cache_usage_perc` 的 telemetry 列,但 `telemetry.py` 实际写入的列名是 `vllm_kv_cache_usage`(没有 `_perc` 后缀)。查找时因为 key 不存在,静默返回 `None`,所以这两个脚本产出的每一份 summary CSV 里,`kv_max_pct` 都是空的。**这两个文件本身没有修复**——本报告用的 `summarize_crossover.py` 用的是正确的列名。如果有人重新跑那两个旧脚本,要知道它们算出来的 `kv_max_pct` 不可信。
